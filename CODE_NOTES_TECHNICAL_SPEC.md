# Техническое задание: плагин XRS Code Notes

## 1. Назначение

Необходимо разработать плагин **XRS Code Notes** для создания заметок, привязанных к конкретным файлам и строкам исходного кода.

Первая реализация создаётся для Visual Studio Code. В дальнейшем плагин планируется портировать на Visual Studio и JetBrains Rider. Функциональное поведение, модель данных и схема SQLite должны быть независимы от конкретного редактора.

По смыслу заметки должны напоминать комментарии в Microsoft Word или ветки комментариев при code review:

- пользователь выбирает строку или диапазон строк;
- создаёт заметку;
- добавляет в неё один или несколько комментариев;
- видит заметку рядом с соответствующим участком кода;
- может переходить по ссылкам из одной заметки в другую;
- может временно полностью выключить отображение и создание заметок.

Плагин не должен изменять содержимое исходных файлов. Все заметки хранятся отдельно в локальной базе SQLite.

## 2. Канонические названия и идентификаторы

Требования к именованию обязательны для всей реализации.

### 2.1. Пользовательское название

Во всех пользовательских интерфейсах, документации, сообщениях, уведомлениях, настройках и заголовках должно использоваться название:

```text
XRS Code Notes
```

Нельзя показывать пользователю старое название `Code Notes` или вариант `xrs-code-notes` в качестве отображаемого названия продукта.

### 2.2. Имя пакета

Имя пакета расширения:

```text
xrs-code-notes
```

Для VS Code это значение должно использоваться как `name` пакета в `package.json`.

### 2.3. Namespace

Все машинные идентификаторы команд, оставшихся настроек и внутренних ключей состояния должны использовать namespace:

```text
xrsCodeNotes
```

Идентификаторы команд должны начинаться с `xrsCodeNotes.`, например:

```text
xrsCodeNotes.addNote
xrsCodeNotes.toggleVisibility
```

Context keys, CommentController, status bar item, Output Channel и остальные внутренние идентификаторы должны использовать `xrsCodeNotes` либо пользовательское название `XRS Code Notes`, в зависимости от того, является значение машинным или отображаемым.

Рекомендуемые идентификаторы:

```text
xrsCodeNotes.commentController
xrsCodeNotes.statusBar
xrsCodeNotes.output
xrsCodeNotes.enabled
xrsCodeNotes.storageReady
xrsCodeNotes.hasSelectedNote
xrsCodeNotes.projectStoragePath
```

Display name CommentController и Output Channel:

```text
XRS Code Notes
```

### 2.4. Основной тип

Основной доменный тип заметки должен называться:

```text
XrsCodeNote
```

Названия DTO могут уточнять назначение, например `XrsCodeNoteRow` или `XrsCodeNoteViewModel`, но основной публичный тип модели остаётся `XrsCodeNote`.

### 2.5. Отсутствие обратной совместимости со старыми именами

Обратная совместимость со следующими элементами не требуется и не должна реализовываться:

- старое отображаемое название `Code Notes`;
- старые namespaces команд или настроек;
- `codeNotes.storageDirectory`;
- `xrs-code-notes.storageDirectory`;
- `xrsCodeNotes.storageDirectory`;
- любая глобальная или project settings-настройка пути;
- старые внутренние идентификаторы;
- файл `code-notes.json`;
- JSON-формат хранения;
- старый формат текстовых ссылок `[[note-id]]`.

Плагин не должен искать, читать, импортировать, изменять или создавать `code-notes.json`.

## 3. Платформенная независимость

Этот документ описывает пользовательское поведение независимо от редактора. Слово «редактор» далее обозначает VS Code, Visual Studio, Rider или другую будущую поддерживаемую IDE.

Каждая платформенная реализация должна:

- использовать официальный публичный API редактора;
- предоставлять одинаковые пользовательские сценарии;
- использовать одну каноническую схему SQLite;
- читать одну и ту же базу `xrs-code-notes.db` без ручной конвертации;
- сохранять одинаковую семантику команд, ссылок и режимов On/Off;
- использовать нативные элементы интерфейса, когда они подходят;
- использовать собственную панель или диалог, если нативного элемента недостаточно;
- не использовать недокументированные команды или внутренние API редактора.

Допустимые технологии:

- VS Code: TypeScript, VS Code Extension API и встроенный модуль `node:sqlite`;
- Visual Studio: C#/.NET, Visual Studio SDK и встраиваемый SQLite-драйвер без отдельной установки SQLite пользователем;
- Rider: Kotlin/Java для IntelliJ frontend и при необходимости C#/.NET для ReSharper backend, с встраиваемым SQLite-драйвером без отдельной установки SQLite.

Поставка адаптеров выполняется поэтапно. Первая версия может содержать только адаптер VS Code. Будущие адаптеры обязаны соблюдать тот же продуктовый контракт и схему базы.

## 4. Термины

**Заметка (`XrsCodeNote`)** — сущность, привязанная к абсолютному пути файла и диапазону строк. Заметка имеет уникальный ID и один или несколько комментариев.

**Комментарий** — запись внутри заметки. Комментарий состоит из обычного текста и, при необходимости, структурированных ссылок на другие заметки.

**Reference Note** — структурированная ссылка с внутренним ID целевой заметки и отдельным видимым текстом.

**Видимый редактор** — открытая вкладка редактора, реально отображаемая пользователю, включая split view.

**Рабочий диапазон** — видимый диапазон строк, расширенный на 200 строк сверху и снизу.

**Хранилище** — база SQLite с фиксированным именем `xrs-code-notes.db` в выбранной папке.

**Проект** — открытая папка проекта либо сохранённый Workspace/solution с устойчивой идентичностью, предоставленной текущей IDE.

**Привязка хранилища** — приватно сохранённое соответствие между идентичностью проекта и абсолютным путём выбранной папки. Привязка не является общей настройкой плагина и не публикуется вместе с проектом.

## 5. Отдельное хранилище для каждого проекта

Каждый проект должен иметь собственную независимо назначенную папку хранения заметок.

Требования:

- путь не является общей глобальной настройкой для всех проектов;
- выбор или смена хранилища одного проекта не изменяет другие проекты;
- при переключении между проектами используются разные сохранённые привязки;
- заметки разных проектов не объединяются;
- записи между базами автоматически не переносятся и не копируются;
- все функции XRS Code Notes работают только с базой текущего проекта;
- одновременно активное соединение должно быть явно связано с идентичностью текущего проекта.

Пользователь выбирает абсолютный путь к папке, а не к файлу базы. Примеры:

```text
D:\Notes\XRSCodeNotes
```

```text
/home/user/xrs-code-notes
```

- относительные пути не допускаются;
- должна поддерживаться текущая ОС редактора;
- имя базы пользователь не вводит;
- если путь некорректен или не является абсолютным, показать ошибку;
- перед открытием базы проверить, что папка существует и является директорией;
- если папка отсутствует, недоступна или удалена, показать понятную ошибку и предложить выбрать другую;
- если путь существует, но не является папкой, показать ошибку;
- при отсутствии прав чтения или записи показать понятную ошибку;
- абсолютный путь сохраняется только после успешной проверки выбора;
- путь к файлу базы строится из проверенной папки и фиксированного имени `xrs-code-notes.db`.

### 5.1. Идентичность проекта

XRS Code Notes работает только при наличии стабильной идентичности проекта.

Проект определяется:

- открытой одиночной папкой проекта; либо
- сохранённым Workspace текущего редактора; либо
- сохранённым solution/project-контейнером IDE, который является нативным аналогом Workspace.

Для сохранённого multi-root Workspace используется одна привязка хранилища на весь Workspace. Для окна с одной папкой используется идентичность этой папки.

Временный или несохранённый Workspace без устойчивого идентификатора не считается подходящим проектом. Пользователю необходимо предложить сохранить Workspace либо открыть обычную папку.

Если открыто пустое окно без папки и без сохранённого Workspace, плагин не должен создавать базу или привязку. Пользователю необходимо показать:

```text
XRS Code Notes: сначала откройте папку проекта или сохранённый Workspace.
```

Команды, которым требуется база, в таком окне должны завершаться без изменения данных.

### 5.2. Приватное состояние проекта

Привязка должна храниться во внутреннем локальном состоянии IDE, относящемся к текущему проекту или Workspace.

Для VS Code обязателен `ExtensionContext.workspaceState`. Абсолютный путь нельзя записывать:

- в User Settings;
- в Workspace Settings;
- в `.vscode/settings.json`;
- в `.code-workspace`;
- в исходные файлы проекта;
- в саму базу как средство обнаружения базы.

Рекомендуемый внутренний ключ VS Code:

```text
xrsCodeNotes.projectStoragePath
```

Для Visual Studio и Rider необходимо использовать эквивалентное приватное локальное project/workspace state, которое не коммитится в репозиторий и не становится общей настройкой других проектов.

### 5.3. Первоначальный выбор

При первом открытии проекта плагин должен проверить, существует ли сохранённая привязка.

Если привязки нет:

1. предложить пользователю выбрать папку;
2. открыть нативный folder picker;
3. проверить выбранный абсолютный путь;
4. только после подтверждения создать или открыть `xrs-code-notes.db`;
5. только после успешного открытия базы сохранить привязку в приватном состоянии проекта.

Пользователь может отменить выбор. При отмене:

- база не создаётся;
- привязка не сохраняется;
- проект остаётся в состоянии `storage not configured`;
- плагин не должен немедленно повторно открывать диалог в цикле;
- следующая пользовательская операция, требующая хранилища, снова предлагает выбор.

### 5.4. Повторное открытие проекта

При повторном открытии того же проекта плагин должен:

1. получить путь из приватного project/workspace state;
2. проверить, что он абсолютный;
3. проверить существование и тип папки;
4. открыть `<папка>/xrs-code-notes.db`;
5. не показывать folder picker при успешном восстановлении.

Другой проект получает только собственную привязку. Если её нет, для него показывается отдельный первоначальный выбор.

Если восстановленный путь недоступен или удалён, нельзя молча создать базу в другом месте. Необходимо показать ошибку и действия повторной попытки либо выбора новой папки.

При смене проекта или Workspace в текущем окне плагин должен отменить ожидающие операции, очистить визуальные объекты, закрыть соединение прежнего проекта и заново выполнить восстановление для новой идентичности. Repository прежнего проекта нельзя переиспользовать после переключения.

### 5.5. Отсутствие общей настройки

Настройка `xrsCodeNotes.storageDirectory` не должна регистрироваться или отображаться в Settings.

Обратная совместимость со старой глобальной настройкой пути не требуется. Плагин не должен читать её, мигрировать её значение или использовать как fallback.

## 6. Файл хранилища и SQLite

В выбранной папке плагин должен автоматически создавать и использовать файл:

```text
xrs-code-notes.db
```

Пользователь не должен создавать базу, таблицы или индексы вручную.

### 6.1. Требование для VS Code

Реализация VS Code должна использовать встроенный в среду выполнения модуль:

```text
node:sqlite
```

SQLite не должен требовать отдельной установки на компьютер пользователя. Нельзя требовать системный `sqlite3`, отдельный сервер, внешнюю службу или ручную установку нативной библиотеки.

Минимальная версия VS Code в `engines.vscode` должна гарантировать наличие требуемого API `node:sqlite` во встроенной версии Node.js. Это ограничение необходимо указать в документации пакета.

### 6.2. Требование для будущих портов

Адаптеры Visual Studio и Rider должны использовать встроенный или поставляемый вместе с плагином SQLite-драйвер. Пользователь не должен отдельно устанавливать SQLite. Драйвер обязан быть совместим с канонической схемой и значением `PRAGMA user_version`.

## 7. Инициализация и параметры базы

При первом открытии новой базы плагин должен в одной контролируемой процедуре:

1. открыть соединение;
2. включить обязательные PRAGMA;
3. создать таблицы;
4. создать индексы и ограничения;
5. установить версию схемы;
6. зафиксировать транзакцию только после успешного завершения всех шагов.

Для каждого соединения обязательны:

```sql
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;
```

Для базы должен быть включён WAL:

```sql
PRAGMA journal_mode = WAL;
```

Требования:

- фактическое значение `journal_mode` необходимо проверить;
- `foreign_keys` необходимо включать на каждом новом соединении;
- `busy_timeout` должен предотвращать немедленные ошибки при кратковременной блокировке;
- `synchronous = NORMAL` используется как безопасный и производительный режим совместно с WAL;
- ошибка установки обязательных параметров должна прерывать инициализацию;
- соединения и prepared statements должны корректно закрываться при деактивации или смене папки.

## 8. Версия схемы

Версия схемы хранится только в:

```sql
PRAGMA user_version;
```

Пользователь не управляет этим значением вручную через интерфейс.

Требования:

- новая база получает текущую версию схемы автоматически;
- текущая версия первой реализации — `1`;
- при открытии версия проверяется до обычных операций;
- если версия новее поддерживаемой, база открывается без изменений и запись запрещается;
- пользователю показывается понятное сообщение о несовместимой версии;
- поддерживаемые миграции выполняются последовательно и в транзакции;
- при неуспешной миграции транзакция откатывается;
- версия плагина и `user_version` являются независимыми значениями.

## 9. Каноническая схема данных

Заметки и комментарии должны храниться в отдельных связанных таблицах. Ссылки внутри комментариев должны храниться структурированно, чтобы ID цели не отображался пользователю.

Минимальная логическая схема версии 1:

```sql
CREATE TABLE notes (
    id          TEXT PRIMARY KEY NOT NULL,
    file_path   TEXT NOT NULL,
    file_key    TEXT NOT NULL,
    start_line  INTEGER NOT NULL CHECK (start_line >= 1),
    end_line    INTEGER NOT NULL CHECK (end_line >= start_line),
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);

CREATE TABLE comments (
    id          TEXT PRIMARY KEY NOT NULL,
    note_id     TEXT NOT NULL,
    position    INTEGER NOT NULL CHECK (position >= 0),
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL,
    FOREIGN KEY (note_id) REFERENCES notes(id) ON DELETE CASCADE,
    UNIQUE (note_id, position)
);

CREATE TABLE comment_segments (
    id              INTEGER PRIMARY KEY,
    comment_id      TEXT NOT NULL,
    position        INTEGER NOT NULL CHECK (position >= 0),
    kind            TEXT NOT NULL CHECK (kind IN ('text', 'noteReference')),
    text            TEXT NOT NULL,
    target_note_id  TEXT,
    FOREIGN KEY (comment_id) REFERENCES comments(id) ON DELETE CASCADE,
    UNIQUE (comment_id, position),
    CHECK (
        (kind = 'text' AND target_note_id IS NULL) OR
        (kind = 'noteReference' AND target_note_id IS NOT NULL)
    )
);
```

`comment_segments.text` означает:

- обычный текст для `kind = 'text'`;
- видимый label гиперссылки для `kind = 'noteReference'`.

`target_note_id` не должен иметь внешний ключ на `notes.id`: удаление целевой заметки не должно удалять чужой комментарий. В этом случае ссылка становится неразрешимой, а интерфейс сообщает, что цель не найдена.

Обязательные индексы:

```sql
CREATE INDEX idx_notes_file_range
    ON notes(file_key, start_line, end_line);

CREATE INDEX idx_notes_file_path
    ON notes(file_key);

CREATE INDEX idx_comments_note_position
    ON comments(note_id, position);

CREATE INDEX idx_segments_comment_position
    ON comment_segments(comment_id, position);

CREATE INDEX idx_segments_target_note
    ON comment_segments(target_note_id)
    WHERE target_note_id IS NOT NULL;
```

`notes.id` и `comments.id` индексируются их `PRIMARY KEY`.

Схема может быть технически расширена, но нельзя менять её семантику, нарушать совместимость адаптеров или удалять перечисленные ограничения и индексы без миграции `user_version`.

## 10. Правила модели данных

- основной тип заметки называется `XrsCodeNote`;
- ID заметки уникален, постоянен и генерируется плагином;
- ID комментария уникален и генерируется плагином;
- `file_path` содержит абсолютный путь, пригодный для открытия;
- `file_key` содержит нормализованный ключ пути для поиска и сравнения;
- алгоритм `file_key` должен быть одинаковым внутри адаптеров на одной ОС;
- номера строк в базе начинаются с `1`;
- `start_line` и `end_line` входят в диапазон;
- для одной строки значения равны;
- `start_line` и `end_line` хранят исходный выбранный пользователем диапазон;
- визуальная позиция gutter-маркера не хранится как замена диапазона и вычисляется отдельно;
- создание, редактирование и удаление комментариев не изменяет `start_line` и `end_line`;
- изменение временной позиции маркера из-за длины документа не изменяет `start_line` и `end_line`;
- платформенный адаптер преобразует номера строк в систему координат API редактора;
- даты хранятся в ISO 8601 UTC;
- заметка должна содержать минимум один комментарий;
- удаление последнего комментария удаляет заметку;
- `ON DELETE CASCADE` автоматически удаляет комментарии и их сегменты при удалении заметки;
- порядок комментариев и сегментов определяется полем `position`.

## 11. Транзакции и операции записи

Все составные изменения должны выполняться в SQLite-транзакциях.

К составным операциям относятся:

- создание заметки, первого комментария и его сегментов;
- добавление комментария с несколькими сегментами;
- редактирование текста и ссылок комментария;
- изменение порядка комментариев или сегментов;
- удаление последнего комментария вместе с заметкой;
- миграция схемы.

Требования:

- при ошибке транзакция полностью откатывается;
- нельзя оставлять комментарий без заметки;
- нельзя частично сохранить составной комментарий;
- добавление или изменение одной заметки не должно читать или перезаписывать всю базу;
- нельзя создавать полную in-memory копию хранилища;
- нельзя применять `structuredClone` или аналог к полному набору заметок;
- SQL должен использовать параметры, а не конкатенацию пользовательского ввода;
- часто используемые запросы должны использовать prepared statements.

## 12. Загрузка заметок и виртуализация

Плагин рассчитан минимум на 100 000 заметок в одном хранилище.

Плагин не должен:

- загружать все заметки проекта в оперативную память;
- читать все комментарии при запуске;
- создавать CommentThread или аналогичный UI-объект для каждой заметки;
- поддерживать полный зеркальный объект базы в памяти;
- выполнять полный table scan при обычной прокрутке редактора.

Заметки загружаются только для файлов, открытых в **видимых редакторах**.

Для каждого видимого диапазона необходимо сформировать рабочий диапазон:

```text
queryStart = max(1, visibleStart - 200)
queryEnd   = visibleEnd + 200
```

Если один файл показан в нескольких split editors, рабочие диапазоны следует объединить, если они пересекаются или соприкасаются.

SQL-запрос должен выбирать только заметки, пересекающие рабочий диапазон:

```sql
WHERE file_key = :fileKey
  AND start_line <= :queryEnd
  AND end_line >= :queryStart
```

Запрос должен использовать составной индекс `idx_notes_file_range`.

Комментарии и сегменты следует загружать только для выбранных ID заметок, а не для всего файла или проекта.

Если рабочий диапазон включает последнюю строку текущего документа, необходимо дополнительно запросить заметки, чья исходная начальная строка больше текущего количества строк:

```sql
WHERE file_key = :fileKey
  AND start_line > :documentLineCount
```

Такие заметки считаются временно вышедшими за пределы документа и группируются на последней доступной строке. Дополнительный запрос обязан использовать индекс по `file_key` и `start_line`, иметь лимит и подчиняться общему ограничению UI-объектов. Он не должен выполняться, пока последняя строка не попала в рабочий диапазон.

## 13. Ограничение UI-объектов

Одновременно должно отображаться не более:

```text
500 CommentThread на один файл
```

Требования:

- ограничение применяется к совокупности видимых экземпляров одного файла;
- при результате более 500 приоритет имеют заметки, пересекающие непосредственно видимые строки;
- оставшиеся места заполняются заметками из 200-строчного запаса по расстоянию до видимого диапазона;
- запрос должен уметь определить факт усечения, например через `LIMIT 501`;
- при усечении плагин должен записать диагностическое событие и может показать ненавязчивое сообщение;
- лимит нельзя обходить созданием дополнительных скрытых CommentThread.

Если одна агрегированная точка содержит более 500 заметок, её раскрытие не должно обходить лимит. Интерфейс обязан использовать виртуализацию, постраничное продолжение или `Load more`, сохраняя единое состояние раскрытия группы. Все заметки остаются доступными пользователю, но одновременно нельзя материализовать более 500 CommentThread для файла.

## 14. Обновление при прокрутке

Плагин должен реагировать на изменение видимого диапазона с небольшой задержкой, предотвращающей слишком частые запросы.

Требования:

- использовать debounce; рекомендуемое начальное значение — 100 мс;
- новая прокрутка до истечения debounce заменяет предыдущий ожидающий запрос;
- устаревший асинхронный результат нельзя применять после более нового запроса;
- закрытие редактора отменяет его ожидающие обновления;
- запрос не выполняется повторно, если новый рабочий диапазон уже покрыт загруженным диапазоном и данные не были инвалидированы.

Для каждого файла должны поддерживаться два ограниченных реестра:

```text
(fileKey, anchorLine) -> агрегированная точка + expanded + revision
noteId -> CommentThread/визуальный объект + groupKey + revision
```

При обновлении диапазона необходимо вычислить разницу:

- неизменившиеся заметки и CommentThread переиспользуются;
- новые заметки создают новые UI-объекты;
- ушедшие из диапазона объекты удаляются;
- изменившаяся заметка обновляет только свой объект;
- изменение длины документа перегруппирует только заметки, чей вычисленный anchor изменился;
- неизменившиеся агрегированные точки переиспользуются;
- все потоки файла нельзя пересоздавать без необходимости.

## 15. Точечная инвалидация

Добавление, изменение или удаление заметки должно инвалидировать только:

- соответствующий `file_key`;
- соответствующий диапазон;
- затронутые note ID и CommentThread;
- прежнюю и новую anchor-группу, если вычисленный anchor изменился;
- ссылки, которые непосредственно зависят от удалённой или изменённой цели, если они сейчас отображаются.

Операция с одной заметкой не должна:

- перечитывать все заметки проекта;
- пересоздавать все CommentThread файла;
- перезапрашивать незатронутые открытые файлы;
- перезаписывать всю базу.

## 16. Отображение заметок

В режиме `XRS Code Notes: On` пользователь должен видеть:

- маркер заметки в области номеров строк или нативный маркер комментариев;
- при необходимости подсветку диапазона;
- возможность раскрыть заметку;
- комментарии в установленном порядке;
- кнопку добавления комментария;
- кнопку `Copy Note ID` в заголовке заметки.

Для VS Code следует использовать Comments API, если оно обеспечивает требования. Допускаются editor decorations и собственная web-панель для отсутствующих возможностей. Visual Studio и Rider используют эквивалентные публичные API.

Плагин не добавляет служебный текст в исходный файл.

### 16.1. Исходный диапазон и точка отображения

Необходимо строго разделять:

- **сохранённый диапазон** — `start_line..end_line` в SQLite;
- **точку отображения** — строку, на которой находится gutter-маркер и к которой привязан визуальный контейнер комментариев.

Точка отображения вычисляется и не записывается вместо исходного диапазона:

```text
anchorLine = min(max(start_line, 1), max(documentLineCount, 1))
```

Правила:

- для многострочной заметки маркер находится на `start_line`, а не на `end_line`;
- для однострочной заметки маркер находится на единственной сохранённой строке;
- диапазон 10–14 даёт маркер на строке 10;
- `end_line` никогда не используется как anchor gutter-маркера;
- изменение комментария, добавление комментария, удаление комментария и изменение ссылок не перемещают маркер;
- вычисление fallback anchor не изменяет строки в SQLite;
- после перезапуска редактора anchor заново вычисляется из сохранённого `start_line` и текущей длины документа;
- при ленивой повторной отрисовке используется тот же алгоритм, поэтому маркер не может переместиться на последнюю строку сохранённого диапазона.

Для VS Code `CommentThread.range`, отвечающий за точку маркера, должен быть привязан к первой строке заметки или fallback anchor как к однострочной/свёрнутой позиции. Полный сохранённый диапазон следует подсвечивать отдельно и использовать при навигации. Нельзя передавать `end_line` как позицию маркера только ради отображения полного диапазона.

### 16.2. Несколько заметок на одной строке

Все заметки, имеющие одинаковые `file_key` и вычисленный `anchorLine`, образуют визуальную группу.

Требования к группе:

- в gutter отображается одна агрегированная точка группы;
- если API позволяет, точка показывает количество заметок;
- по нажатию на точку все заметки группы раскрываются после anchor-строки подряд;
- повторное нажатие на ту же точку сворачивает все заметки группы одновременно;
- заметки не должны перекрывать друг друга или появляться после разных строк;
- для заметок с одинаковым исходным `start_line` окна располагаются после этой первой строки;
- группа сохраняет отдельные note ID, комментарии и кнопки `Copy Note ID`;
- раскрытие или сворачивание является только UI-состоянием и не изменяет SQLite.

Детерминированный порядок заметок внутри группы:

```text
start_line ASC,
end_line ASC,
created_at ASC,
id ASC
```

Изменение одного комментария не должно пересоздавать остальные окна группы. Удаление одной заметки удаляет только её окно; агрегированная точка исчезает лишь после удаления последней заметки группы.

Если штатный Comments API не позволяет одной точкой раскрывать и сворачивать несколько отдельных заметок, платформенный адаптер должен реализовать агрегированный маркер и управление группой собственным публичным UI-механизмом. Ограничение API редактора не отменяет групповое поведение.

### 16.3. Заметки за пределами текущего документа

Если сохранённый `start_line` больше текущего количества строк файла, исходная строка считается временно недоступной.

В этом случае:

- маркер отображается на последней доступной строке документа;
- `start_line` и `end_line` в SQLite остаются без изменений;
- все заметки, получившие один fallback anchor, отображаются одной агрегированной точкой;
- один клик раскрывает окна этих заметок подряд после последней доступной строки;
- повторный клик сворачивает всю группу;
- исходные диапазоны заметок не объединяются;
- восстановление строк файла автоматически возвращает каждую заметку на её исходный `start_line`, когда эта строка снова становится доступной;
- обновление выполняется через diff, без пересоздания незатронутых групп.

Под «строка недоступна» понимается отсутствие такого номера в текущей версии документа. Плагин не пытается распознавать идентичность текста строки после редактирования: если номер `start_line` всё ещё существует, anchor остаётся на этом номере.

Если API представляет пустой документ как одну виртуальную строку, fallback anchor равен строке 1.

### 16.4. Состояние группы и производительность

- состояние раскрытия хранится только для загруженных групп текущего проекта;
- закрытие файла освобождает состояние его групп;
- повторное открытие может начинаться со свёрнутого состояния;
- комментарии большой группы разрешается подгружать при раскрытии, а не вместе с gutter-маркером;
- сворачивание группы должно освобождать тяжёлые UI-объекты, если они больше не нужны;
- группа участвует в общем лимите 500 CommentThread на файл;
- повторная viewport-загрузка должна переиспользовать агрегированную точку и неизменившиеся окна.

## 17. Создание заметки

Пользовательская команда:

```text
XRS Code Notes: Add Note
```

Машинный ID:

```text
xrsCodeNotes.addNote
```

В режиме On действие доступно через палитру команд, контекстное меню редактора, контекстное меню выделенного диапазона и нативный элемент комментариев, если он существует.

Сценарий:

1. Пользователь ставит курсор на строку или выделяет диапазон.
2. Запускает создание заметки.
3. Открывается графический редактор комментария.
4. Пользователь вводит текст и при необходимости добавляет ссылки.
5. Нажимает `Save`.
6. В одной транзакции создаются заметка, комментарий и сегменты.
7. Созданная заметка точечно добавляется в UI текущего файла.

Если выделения нет, используется текущая строка. Пустой комментарий сохранять нельзя. Отмена не изменяет базу.

## 18. Графический редактор комментария

Создание и редактирование комментария должно выполняться через графический интерфейс с элементами:

- поле текста;
- кнопка `Add Reference Note`;
- кнопка `Save`;
- кнопка `Cancel`;
- отображение добавленных ссылок только по label;
- удаление добавленной ссылки до сохранения.

Для VS Code разрешается Webview, если штатный comment editor не позволяет разместить кнопку. Для других IDE используется нативный диалог, tool window или безопасный эквивалент.

Данные UI валидируются в backend плагина. Закрытие без Save не изменяет базу.

## 19. Добавление Reference Note

Пользователь не вводит служебную конструкцию или внутренний URI вручную.

После нажатия `Add Reference Note`:

1. Открывается Quick Pick или эквивалентный динамический поиск.
2. Пользователь вводит ID или часть ID целевой заметки.
3. Поиск выполняется в SQLite по мере ввода.
4. Один запрос возвращает не более 50 результатов.
5. Весь список заметок не загружается в память.
6. Выбранный ID повторно проверяется точным запросом по primary key.
7. После выбора интерфейс запрашивает отображаемый текст ссылки.
8. Пустой label не допускается.
9. В комментарий добавляется `noteReference` с label и скрытым target ID.

Поиск должен использовать debounce и отмену либо игнорирование устаревших результатов. Рекомендуемая задержка — 150 мс.

В сохранённом и отображаемом комментарии пользователь видит только кликабельный label. ID не отображается рядом со ссылкой.

## 20. Поиск заметок

Поиск по точному ID выполняется индексированным запросом к `notes.id`.

Поиск для открытого файла и диапазона выполняется через `idx_notes_file_range`.

Интерфейс выбора заметки:

- не выполняет `SELECT * FROM notes` без ограничения;
- не материализует все результаты;
- возвращает максимум 50 строк;
- должен поддерживать точный ID и индексируемый префикс ID;
- может дополнительно искать по пути файла, если это реализовано без полной загрузки данных;
- должен переиспользовать prepared statement;
- должен применять только результат последнего пользовательского ввода.

Если добавляется полнотекстовый поиск, он должен иметь отдельный индекс SQLite и миграцию схемы. Полный scan комментариев при каждом символе запрещён.

## 21. Переход к заметке

При нажатии на видимый label ссылки, вызове `Go to Note` или другом переходе к заметке плагин должен:

1. выполнить индексированный поиск цели по ID;
2. проверить существование файла;
3. открыть файл;
4. прочитать исходные `start_line` и `end_line` из SQLite;
5. перейти к `start_line`;
6. выделить весь сохранённый включительный диапазон от `start_line` до `end_line`;
7. загрузить целевую заметку, даже если она ранее находилась вне рабочего диапазона;
8. раскрыть её визуальную группу и конкретную заметку;
9. перевести фокус на заметку.

Для диапазона 10–14 переход обязан выделить строки 10–14, хотя gutter-маркер расположен на строке 10.

Если сохранённый диапазон частично выходит за текущий конец файла, физически выделяется его доступное пересечение с документом, а пользователю показывается ненавязчивое сообщение о сокращённом отображении. Если `start_line` полностью находится за концом файла, курсор и выделение устанавливаются на последнюю доступную строку, после чего раскрывается fallback-группа. Значения в SQLite не изменяются.

Если заметка не найдена, показать:

```text
XRS Code Notes: целевая заметка не найдена.
```

Если файл отсутствует, показать понятную ошибку с полным путём.

Нельзя исполнять произвольные команды или URI из пользовательского текста. Внутренний переход формируется только из валидированного `noteReference`.

## 22. Copy Note ID

В заголовке каждой сохранённой заметки должна быть кнопка:

```text
Copy Note ID
```

Машинный ID команды:

```text
xrsCodeNotes.copyNoteId
```

По нажатию:

- ID конкретной заметки копируется в системный буфер обмена;
- показывается подтверждение `XRS Code Notes: Note ID copied`;
- ID не отображается постоянно в заголовке или теле заметки.

## 23. Комментарии и удаление

Необходимо поддержать:

- добавление комментария к заметке;
- редактирование текста и ссылок;
- удаление отдельного комментария;
- удаление всей заметки;
- переход к исходному диапазону заметки.

Если удаляется последний комментарий, в той же транзакции удаляется заметка. Удаление заметки автоматически удаляет комментарии и сегменты через foreign keys и `ON DELETE CASCADE`.

Перед удалением всей заметки необходимо запросить подтверждение.

После операции обновляются только затронутые строки БД и UI-объекты.

Добавление, редактирование или удаление комментария не должно менять сохранённый диапазон заметки, её вычисленный anchor или положение агрегированной точки. Исключение — удаление последнего комментария, при котором удаляется сама заметка и пересчитывается состав её группы.

## 24. Режимы On/Off

В строке состояния находится постоянный переключатель:

```text
XRS Code Notes: On
XRS Code Notes: Off
```

Для VS Code рекомендуемые значения:

```text
status bar id: xrsCodeNotes.statusBar
command id: xrsCodeNotes.toggleVisibility
context key: xrsCodeNotes.enabled
```

В другой IDE используется эквивалентная постоянная кнопка в строке состояния или основной панели.

Состояние сохраняется в штатном постоянном хранилище настроек редактора, но не в SQLite-базе заметок.

Режим On/Off и готовность project storage являются разными состояниями. On не означает, что база уже назначена. Если проект не имеет привязки, операция, требующая базы, должна запустить сценарий первоначального выбора. В пустом окне без стабильной идентичности проекта операция должна показать требование сначала открыть проект.

### 24.1. Режим Off

В режиме Off плагин должен полностью убрать из редактора исходного кода:

- CommentThread и раскрытые комментарии;
- подсветку диапазонов;
- gutter-маркеры;
- inline-аннотации;
- элементы добавления заметок;
- остальные визуальные элементы XRS Code Notes внутри редактора.

Переключатель On/Off остаётся видимым.

В режиме Off:

- нельзя создавать заметки;
- нельзя добавлять или редактировать комментарии;
- соответствующие команды и пункты меню скрыты или disabled;
- каждый обработчик дополнительно проверяет `xrsCodeNotes.enabled`;
- программный вызов команды изменения не должен обходить запрет;
- существующие данные не удаляются;
- визуальные запросы заметок для viewport не выполняются.

### 24.2. Повторное включение

При переходе в On плагин должен:

- восстановить команды создания;
- запросить заметки только для текущих видимых диапазонов с запасом 200 строк;
- создать не более 500 CommentThread на файл;
- не загружать остальные заметки;
- восстановить функциональность без потери данных.

## 28. Выбор и смена хранилища текущего проекта

Должна быть доступна команда:

```text
XRS Code Notes: Select Storage Folder for This Project
```

с ID:

```text
xrsCodeNotes.selectStorageFolderForProject
```

Команда должна:

1. проверить наличие стабильной идентичности текущего проекта;
2. открыть нативный folder picker;
3. позволить отмену без изменений;
4. проверить абсолютность, существование, тип и доступность выбранной папки;
5. вычислить путь `<выбранная папка>/xrs-code-notes.db`;
6. открыть и полностью проверить новую базу до окончательного переключения;
7. запретить новые операции со старым repository;
8. отменить ожидающие viewport-запросы;
9. завершить активные операции либо безопасно откатить их;
10. закрыть prepared statements и предыдущее соединение;
11. заменить привязку только в приватном состоянии текущего проекта;
12. удалить UI-объекты старой базы;
13. открыть repository новой базы;
14. в режиме On загрузить заметки новой базы только для видимых диапазонов;
15. показать сообщение с новым абсолютным путём.

Рекомендуемое сообщение:

```text
XRS Code Notes: storage for this project changed to <абсолютный путь>.
```

Если проверка или открытие новой базы завершились ошибкой, старая привязка и работоспособное старое соединение должны по возможности сохраниться. Нельзя оставлять проект привязанным к неоткрываемой базе.

При смене папки запрещено:

- изменять project state другого проекта;
- автоматически копировать заметки из прежней базы;
- объединять записи старой и новой базы;
- удалять прежнюю базу;
- использовать глобальную настройку как fallback.

## 29. Изменение исходного кода

В базе хранится исходная привязка по номерам строк. Обычное редактирование документа не должно автоматически переписывать `start_line` и `end_line`.

После изменения документа адаптер должен:

1. получить актуальное количество строк;
2. пересчитать только вычисленные anchor для загруженных заметок этого файла;
3. перегруппировать затронутые визуальные точки через diff;
4. оставить сохранённые диапазоны без изменений;
5. не перечитывать и не пересоздавать все заметки проекта.

Если `start_line` остаётся доступным номером, маркер остаётся на нём, даже если текст этой строки изменился. Если `start_line` превышает текущую длину файла, маркер временно переходит на последнюю доступную строку и входит в её агрегированную группу.

Если файл снова увеличился и исходный `start_line` стал доступен, заметка автоматически возвращается с fallback-группы на исходную первую строку. Это перемещение является только визуальным.

Известное ограничение: плагин не отслеживает semantic identity строки. После вставки или удаления строк выше заметки сохранённый номер может соответствовать другому фрагменту кода. Устойчивые content anchors являются отдельной будущей функцией.

Полнотекстовая копия исходных файлов, скрытая модификация сохранённых диапазонов и ненадёжное массовое переписывание строк запрещены.

`ProjectStorageManager` не должен иметь один безусловный глобальный путь. Открытый repository всегда маркируется идентичностью проекта; несовпадение текущей идентичности и владельца repository блокирует операцию до корректного переключения.

### 30.1. Граница repository

UI и команды не должны выполнять SQL напрямую. Repository должен предоставлять точечные операции, например:

deleteComment(commentId)
deleteNote(noteId)

Методы выборки возвращают только необходимые строки. Метод получения всех заметок проекта не должен существовать в production API.

- VS Code, Visual Studio и Rider используют одинаковые table/column names и `user_version`;
- ID не пересоздаются при открытии базы другой IDE;

- внешняя установка SQLite не требуется ни для одного адаптера.

## 31. Безопасность

- весь текст комментариев считается недоверенным вводом;
- SQL использует bound parameters;
- Markdown и HTML экранируются;
- произвольный HTML запрещён;
- произвольные command URI запрещены;
- навигационные ссылки формируются только из `noteReference`;
- web-панель должна иметь Content Security Policy;
- скрипты web-панели должны использовать nonce или эквивалент;
- все сообщения UI валидируются в backend;
- UI не получает произвольный доступ к файловой системе;
- путь базы строится только из проверенной папки и фиксированного имени.
- привязка пути хранится только в приватном project/workspace state текущей IDE;
- путь не записывается в файлы настроек или исходные файлы проекта;
- проектная идентичность проверяется до чтения или изменения привязки;

## 32. Производительность и жизненный цикл

Целевая нагрузка:

```text
не менее 100 000 заметок и 100 000 комментариев
```

При такой нагрузке запрещены:

- полная загрузка базы в память;
- создание 100 000 UI-объектов;
- полное клонирование состояния;
- перезапись всего хранилища;
- запрос без диапазона для обычного отображения редактора;
- неограниченный запрос для Quick Pick.

Плагин должен:

- использовать prepared statements;
- использовать транзакции для batch insert и составных изменений;
- освобождать subscriptions, UI-объекты, statements и соединения;
- применять debounce для viewport и поиска;
- не блокировать UI-поток длительными синхронными операциями;
- хранить в памяти только состояние видимых файлов, ограниченные результаты поиска и небольшой служебный кэш;
- загружать тела комментариев агрегированной группы лениво при раскрытии, если они ещё не нужны для отображения маркера;
- группировать заметки по anchor без создания дубликатов моделей или полного клонирования результатов;
- не допускать роста heap пропорционально полному количеству заметок при обычном открытии проекта.

SQLite API может быть синхронным на уровне `node:sqlite`; в этом случае запросы должны быть строго ограниченными и индексированными. Массовое заполнение и benchmark не должны выполняться в обычном пользовательском UI-потоке.

## 33. Нагрузочный тест 100k

В проекте должен присутствовать воспроизводимый нагрузочный тест, запускаемый командой:

```text
npm run benchmark:100k
```

Тест должен:

1. создать отдельную временную базу;
2. применить production-схему и PRAGMA;
3. с детерминированным seed создать 100 000 заметок;
4. создать 100 000 комментариев, связанных с заметками;
5. распределить заметки по множеству файлов и диапазонов;
6. включить заметки с одинаковым `start_line` для проверки групп;
7. включить заметки со `start_line` за пределами тестовой длины документа;
8. использовать production repository или тот же SQL-слой;
9. не использовать заранее подготовленную скрытую базу;
10. удалить временные данные после завершения либо явно вывести их путь при режиме сохранения результатов.

Тест должен измерять и выводить:

- время первоначального создания и заполнения базы;
- время загрузки заметок для видимого диапазона с запасом 200 строк;
- количество строк, прочитанных range query;
- время точного поиска по ID;
- время Quick Pick query с лимитом 50;
- время запроса fallback-заметок на последней строке;
- время diff-перегруппировки при изменении длины документа;
- время изменения одного комментария в транзакции;
- heap до заполнения, после заполнения и после принудительного освобождения доступных ресурсов;
- пиковое либо максимально наблюдаемое потребление heap;
- версию Node.js, SQLite, ОС и основные параметры запуска.

Результаты должны быть воспроизводимыми и выводиться в читаемом виде, а также желательно сохраняться как JSON-отчёт. Для операций с коротким временем следует выполнять серию прогонов и выводить median и p95.

Benchmark не должен создавать CommentThread. Отдельный интеграционный тест должен подтвердить, что при базе 100k UI-регистр не превышает 500 объектов на файл.

## 34. Функциональные тесты

### 34.1. Именование

- package name равен `xrs-code-notes`;
- display name равен `XRS Code Notes`;
- все command IDs начинаются с `xrsCodeNotes.`;
- настройка `xrsCodeNotes.storageDirectory` не зарегистрирована;
- CommentController, context keys, status bar и Output Channel используют требуемые имена;
- основной тип называется `XrsCodeNote`;
- старые имена не регистрируются.

### 34.2. Проектная привязка хранилища

- пустое окно без проекта не создаёт базу и показывает требование открыть проект;
- новая одиночная папка получает отдельный первоначальный выбор;
- сохранённый Workspace получает собственный выбор;
- отмена первоначального выбора не создаёт базу и не сохраняет путь;
- следующая операция после отмены повторно предлагает выбор;
- абсолютный путь сохраняется только после успешного открытия базы;
- повторное открытие проекта восстанавливает путь без folder picker;
- другой проект не получает путь первого проекта;
- VS Code хранит путь в `workspaceState`;
- путь отсутствует в User Settings, Workspace Settings, `.vscode/settings.json` и `.code-workspace`;
- удалённая или недоступная папка даёт понятную ошибку;
- `xrsCodeNotes.selectStorageFolderForProject` меняет только текущий проект;
- отмена смены сохраняет прежнюю привязку;
- ошибка открытия новой базы по возможности сохраняет прежнее рабочее соединение;
- успешная смена закрывает старое соединение, обновляет видимые заметки и показывает новый путь;
- при смене база не копируется, не объединяется и не удаляется.

### 34.3. SQLite

- автоматическое создание `xrs-code-notes.db`;
- отсутствие создания `code-notes.json`;
- создание таблиц, индексов и ограничений;
- установка и проверка `user_version`;
- включение WAL, foreign keys, busy timeout и synchronous NORMAL;
- cascade delete комментариев;
- rollback составной операции;
- отказ при несовместимой версии;
- понятная ошибка при повреждённой базе;
- использование `node:sqlite` в адаптере VS Code без внешней установки.

### 34.4. Виртуализация

- запросы выполняются только для видимых редакторов;
- диапазон расширяется ровно на 200 строк с каждой стороны с ограничением снизу в 1;
- выбираются только пересекающие заметки;
- split ranges объединяются;
- создаётся не более 500 CommentThread на файл;
- неизменившиеся потоки переиспользуются;
- устаревший результат прокрутки не применяется;
- изменение одной заметки не перезагружает остальные файлы;
- обычное открытие проекта не загружает 100 000 заметок в heap.

### 34.5. Anchor и группировка заметок

- однострочная заметка 10–10 имеет маркер на строке 10;
- многострочная заметка 10–14 имеет маркер на строке 10, а не 14;
- переход к заметке 10–14 выделяет весь диапазон 10–14;
- `start_line` и `end_line` не меняются при вычислении anchor;
- добавление, редактирование и удаление комментария не перемещает маркер;
- после перезапуска маркер восстанавливается из `start_line`;
- lazy rerender не перемещает маркер на `end_line`;
- несколько заметок с одной первой строкой образуют одну gutter-точку;
- раскрытие точки показывает заметки подряд в детерминированном порядке;
- повторное нажатие сворачивает всю группу;
- изменение одной заметки не пересоздаёт неизменившиеся окна группы;
- удаление последней заметки удаляет агрегированную точку;
- при `start_line > documentLineCount` anchor равен последней доступной строке;
- несколько out-of-bounds заметок образуют одну fallback-точку на последней строке;
- fallback-группа раскрывается и сворачивается целиком;
- возврат достаточного количества строк возвращает заметки на исходные anchor;
- SQLite-диапазоны не меняются при fallback и восстановлении;
- out-of-bounds query выполняется только возле последней строки и имеет лимит;
- группа более 500 заметок не создаёт более 500 CommentThread одновременно.

### 34.6. Поиск

- точный ID использует индекс;
- range query использует `idx_notes_file_range`;
- Quick Pick query возвращает максимум 50 результатов;
- ввод обрабатывается динамически с debounce;
- весь список не материализуется;
- устаревший результат поиска игнорируется.

Для ключевых запросов тесты должны проверять `EXPLAIN QUERY PLAN`, чтобы защититься от случайного перехода к полному scan.

### 34.7. Функции пользователя

- создание заметки для строки и диапазона;
- несколько комментариев в заметке;
- редактирование и удаление;
- удаление заметки после последнего комментария;
- `Add Reference Note` и скрытый target ID;
- переход по ссылке;
- ошибка при отсутствующей цели;
- `Copy Note ID`;
- ID не отображается постоянно;
- режим Off очищает UI и запрещает изменения;
- повторный On восстанавливает только видимые заметки;
- Show Storage File открывает системный файловый менеджер.
- все функции используют repository текущего проекта.

## 35. Критерии приёмки

Платформенная реализация считается готовой, если:

1. Во всём UI используется название `XRS Code Notes`.
2. Package name равен `xrs-code-notes`.
3. Команды, оставшиеся настройки и внутренние ключи используют namespace `xrsCodeNotes`.
4. Основной тип называется `XrsCodeNote`.
5. Общая настройка `xrsCodeNotes.storageDirectory` отсутствует.
6. Каждый проект имеет отдельную привязку к хранилищу в приватном локальном project/workspace state.
7. В VS Code привязка хранится через `workspaceState` и не попадает в `.vscode/settings.json` или `.code-workspace`.
8. Пустое окно без стабильной идентичности проекта не создаёт базу и просит открыть проект.
9. При первом открытии проекта предлагается выбрать папку, а отмена не создаёт базу.
10. Повторное открытие проекта восстанавливает путь без повторного диалога.
11. Другой проект использует только собственную привязку и при её отсутствии получает отдельный выбор.
12. Плагин автоматически создаёт `xrs-code-notes.db` в выбранной папке.
13. Команда `xrsCodeNotes.selectStorageFolderForProject` меняет базу только текущего проекта.
14. Смена базы закрывает прежнее соединение, открывает новое, обновляет UI и сообщает новый путь.
15. При смене заметки не копируются, не объединяются и не переносятся.
16. `code-notes.json` нигде не создаётся и не читается.
17. SQLite не требует отдельной установки; VS Code использует `node:sqlite`.
18. Таблицы, индексы, constraints и `user_version` создаются автоматически.
19. WAL, foreign keys, busy timeout и synchronous NORMAL активны.
20. Заметки и комментарии находятся в связанных таблицах, а cascade delete работает.
21. Составные изменения транзакционны.
22. Пользователь создаёт, редактирует и удаляет заметки и комментарии в базе текущего проекта.
23. Ссылки добавляются через `Add Reference Note`, а ID скрыт.
24. Ссылка открывает файл, диапазон и целевую заметку текущего хранилища.
25. `Copy Note ID` копирует ID и показывает подтверждение.
26. Режим Off полностью очищает редактор и запрещает изменения.
27. Повторный On восстанавливает функциональность без полной загрузки базы.
28. Загружаются только заметки видимых файлов и рабочих диапазонов ±200 строк.
29. На один файл существует не более 500 CommentThread.
30. Прокрутка использует debounce и diff, а неизменившиеся потоки не пересоздаются.
31. CRUD одной заметки обновляет только затронутый файл и UI-объекты.
32. Поиск ID и range query используют SQLite-индексы.
33. Quick Pick выполняет динамические запросы с лимитом 50.
34. Команда хранилища показывает DB в системном файловом менеджере.
35. Ошибки базы и версии схемы понятны пользователю и не приводят к потере данных.
36. Проект работает с базой 100 000 заметок без полной загрузки в память и без 100 000 UI-объектов.
37. `npm run benchmark:100k` воспроизводимо создаёт 100 000 заметок и 100 000 комментариев и выводит требуемые метрики.
38. Оптимизации не нарушают создание, редактирование, удаление, ссылки, копирование ID, навигацию и On/Off.
39. Маркер многострочной заметки находится на `start_line`, а не на `end_line`.
40. Заметка 10–14 отображает маркер на строке 10, а переход выделяет строки 10–14.
41. CRUD комментариев, перезапуск и lazy rerender не изменяют anchor заметки.
42. Сохранённые `start_line` и `end_line` не изменяются из-за позиции маркера.
43. Заметки с одинаковым anchor имеют одну агрегированную gutter-точку и выводятся после строки подряд.
44. Один клик раскрывает всю группу, повторный клик сворачивает её целиком.
45. Если `start_line` больше длины документа, заметка отображается в общей fallback-точке на последней доступной строке.
46. Fallback не меняет SQLite-диапазон, а восстановление строк возвращает заметку на исходную первую строку.
47. Группировка и fallback не обходят лимит 500 CommentThread и не вызывают полную загрузку базы.

## 36. Что не входит в первую версию

Если отдельно не согласовано иное, в первую версию не входят:

- импорт `code-notes.json`;
- совместимость со старыми командами и настройками;
- импорт или миграция глобальной настройки пути;
- автоматическое копирование заметок при выборе другой папки;
- облачная синхронизация;
- одновременное совместное редактирование несколькими пользователями;
- автоматическое объединение разных баз;
- устойчивые semantic anchors после произвольных рефакторингов;
- вложения и изображения;
- полнотекстовый поиск без отдельного SQLite-индекса;
- одновременная поставка портов Visual Studio и Rider вместе с первой версией VS Code;
- публикация в маркетплейсе, если она не запрошена отдельно.

## 37. Приоритет требований

Этот документ полностью заменяет предыдущие варианты ТЗ в конфликтующих частях.

Особенно обязательны:

- название `XRS Code Notes`, package `xrs-code-notes` и namespace `xrsCodeNotes`;
- основной тип `XrsCodeNote`;
- отдельная приватная привязка хранилища для каждого проекта;
- `workspaceState` для привязки в VS Code и эквивалентное локальное project state в других IDE;
- отсутствие `xrsCodeNotes.storageDirectory` в Settings и файлах проекта;
- обязательная стабильная идентичность проекта;
- первоначальный выбор с возможностью отмены и автоматическое восстановление пути;
- безопасная смена базы только текущего проекта без копирования или объединения данных;
- только SQLite-файл `xrs-code-notes.db`;
- отсутствие чтения и создания `code-notes.json`;
- `node:sqlite` для VS Code без внешней установки SQLite;
- автоматическая схема и версия в `PRAGMA user_version`;
- транзакции, foreign keys, WAL, busy timeout и synchronous NORMAL;
- точечные индексированные запросы;
- загрузка только видимых файлов и диапазонов ±200 строк;
- максимум 500 CommentThread на файл;
- gutter-маркер на первой строке сохранённого диапазона;
- независимость сохранённого диапазона от вычисленной позиции маркера;
- единая раскрываемая группа для заметок с одинаковым anchor;
- fallback-группа на последней доступной строке для заметок за пределами документа;
- переход с выделением всего сохранённого доступного диапазона;
- diff UI-объектов вместо полного пересоздания;
- динамический Quick Pick с лимитом 50;
- отсутствие полной копии базы в памяти;
- benchmark на 100 000 заметок и 100 000 комментариев;
- сохранение всего ранее согласованного пользовательского функционала.

Реализация не должна упрощать или отменять эти требования со ссылкой на прежнее описание задачи.
